# Datasheet: LLM judge ratings on VerifyBench

Follows the structure of Gebru et al., *Datasheets for Datasets*.

## Motivation

**Why was it created?** To measure how much information repeated queries to an
LLM judge actually carry, and to test whether a latent-variable measurement model
can recover judge error rates and outcome prevalence from those queries.

**Who created it?** [TEAM]. No external funding.

## Composition

**What do instances represent?** One binary judgment by one judge model on one
benchmark item in one sampling round. 52,500 rows.

**Fields.**

| Field | Description |
|---|---|
| `item_id` | Identifier referencing a row of the source benchmark |
| `split` | `VB` (VerifyBench) or `VBH` (VerifyBench-Hard) |
| `gold` | The benchmark's human label, 1 if the completion is correct |
| `model` | Judge model key |
| `arm` | Prompt condition: `verbatim`, `difficulty`, or `noref` |
| `round` | Sampling round, 0 to 9 |
| `verdict` | 1 if the judge said correct, 0 if not, blank if unparseable |
| `difficulty` | Judge's self-reported 1--5 rating, `difficulty` arm only |
| `native_reasoner` | 1 if the judge reasons by default |
| `status` | Parse outcome |

**Is anything missing?** 5.8% of rounds produced no parseable verdict, retained
in `ratings.csv` with a diagnostic status rather than dropped. Failures
concentrate in the smallest judge at 23.3%, with Qwen3.5-9B next at 10.8% and the
remaining five between 0.9% and 2.2%.

`item_level.csv` holds 5,094 rows rather than the 5,250 that 250 items x 3 prompt
arms x 7 judges would give. The 156 absent rows are item-judge-arm combinations in
which every one of the ten rounds failed to parse, so no count could be formed.
Of those, 138 belong to gemma-3-1b, meaning 18.4% of its cells failed completely.
At a 23.3% round-level failure rate, independent failures would almost never
produce a run of ten, so the failures cluster on particular items rather than
occurring at random. The remaining 18 are spread across four other judges.

**Does it contain source text?** No. Item identifiers reference the source
benchmark, which is fetched separately.

**Personal or sensitive data?** None. The benchmark contains reasoning problems
and model-generated completions.

## Collection

**How was it collected?** Seven open-weight models were served with vLLM at their
released precision, checkpoints pinned by commit hash. Each was queried ten times
per item at temperature 0.7 and top-p 0.9 under three prompt conditions. Prompts
are reproduced verbatim from the benchmark authors' published appendices.

**Sampling.** 150 items from VerifyBench, stratified on the gold label and answer
type, at most one completion per question. 100 items from VerifyBench-Hard by
simple random sampling, preserving the natural class imbalance. Fixed seed;
identifiers reference source rows, so a larger draw under the same seed is a
superset.

**Timeframe.** August 2026.

**Human involvement?** None. Gold labels are the benchmark's own, produced by its
authors.

## Preprocessing

Verdicts were extracted by regular expression on the final `Final Judgment:` line.
For the two judges that reason natively, the answer channel is isolated first so
that a verdict mentioned mid-reasoning is not mistaken for the answer. Raw
transcripts are not redistributed.

Recomputing error rates with unparsed rounds counted as correct, counted as
incorrect, or dropped changes the total error rate by at most 0.061, so the
decision to drop them is not load-bearing.

## Uses

**Intended.** Studying LLM judge reliability, evaluating measurement models for
noisy annotations, and as a worked example of estimating error rates without full
ground truth.

**Not appropriate.** These figures do not transfer to other judges, prompts, or
sampling temperatures. Error rates are properties of a specific configuration.
Nor should the dataset be used to rank models, since it covers one benchmark under
one configuration.

**Known limitations.** 250 items from one benchmark. VerifyBench-Hard supplies
only about 24 items with correct completions. About 10% of items have completions
generated by one of the judges evaluated, a self-evaluation overlap we record but
do not correct for. Gold labels are treated as ground truth, though we encountered
cases we found difficult to adjudicate.

## Distribution

Released on GitHub under [CC0 / CC BY 4.0]. Source benchmark text is not
redistributed and remains under its own MIT license.

The repository ships `data/item_ids.csv`, holding the 250 item identifiers with
their published gold labels, and `collection/fetch_items.py`, which joins those
identifiers against the public benchmark to reconstruct the working file locally.
`collection/make_item_ids.py` performs the inverse and documents how the
identifier file was produced.

Raw judge transcripts are not distributed. Judges quote fragments of the question
and completion while reasoning, so the transcripts are a partial reproduction of
benchmark text. `data/ratings.csv` holds the parsed verdicts, which contain no
text at all.
